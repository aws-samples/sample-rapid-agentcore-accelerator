## What this repo is

**RAPID (Rapid Agentic Prototyping & Infrastructure Deployment)** is a monorepo blueprint for deploying agentic AI solutions on Amazon Bedrock AgentCore. It targets prototypes and demos. It is sample code, not production software: prefer working code and fast iteration over polish, abstraction, or defensive engineering.

`config.yaml` is the composition point. One stack, `AgentCore-{deploymentPrefix}`, is synthesized from it. Most changes a user wants are config edits, not CDK edits.

## Repository layout

```text
agent/{name}/src/         Agent source — main.py, tools/, utils/, Dockerfile
agent/{name}/evals/       Optional eval suite (customer-support only)
mcp/{name}/src/           MCP server source (FastMCP) + Dockerfile
knowledge-bases/{name}/   Documents uploaded to that knowledge base on deploy
frontend/src/             Streamlit chat UI
infra/lib/config.ts       Config parser and validator for config.yaml
infra/lib/stacks/         Stack definitions — the composition point
infra/lib/constructs/     Reusable L3 constructs (one folder each)
infra/test/               Jest unit, snapshot, and property tests
scripts/                  Shell helpers, each invoked by a Makefile target
config.yaml               Agents, MCP servers, knowledge bases, and their mappings
```

Each subproject is independent: its own virtual environment, its own `pyproject.toml` or `package.json`, its own deploy lifecycle. Do not hoist dependencies across them.

## Conventions

**Configuration.** `agents` and `mcpServers` are required keys — the loader raises a named error when either is absent rather than falling back to a default directory. Every entry's resolved `sourceDir` must exist on disk. Adding an agent, an MCP server, or a knowledge base means creating the directory *and* adding the `config.yaml` entry; one without the other fails at synth. Key reference: [docs/configuration.md](docs/configuration.md).

**Agents and MCP servers.** An agent picks up knowledge-base retrieval when its `knowledgeBase` field names one, and MCP tools when its `mcpServers` list names one. The wiring is injected as environment variables by CDK — do not hardcode ARNs or IDs in agent source. Environment variables are enumerated in [docs/configuration.md](docs/configuration.md).

**Deploy outputs.** `.rapid/outputs.json` is generated by deployment. It is machine-local and is not tracked. Read it (for example with `jq`) when a script needs an ARN or a bucket name; never edit it by hand and never commit it.

**Constructs.** Only the constructs listed as default-path in [infra/lib/constructs/README.md](infra/lib/constructs/README.md) are instantiated by the stack. Treat anything under *Opt-in* as not exercised by the default deployment, and read that README before modifying any construct.

**Scripts.** `scripts/` contains exactly `chat.sh`, `docker-run.sh`, `doctor.sh`, `enable_cicd.sh`, `ingest-kb-assets.sh`, `logs.sh`, and `write_outputs.sh`. Every one is reachable from a `Makefile` target. If you add a script, add the target too.

Local dev commands are repository-level and agent-agnostic: `chat.sh` and `docker-run.sh` take the agent name as their first argument and resolve everything else from `.rapid/outputs.json`. Adding an agent must not add a shell script — if it seems to need one, the generic script is missing a flag. Neither script parses `config.yaml`; `chat.sh` validates the agent against the deployed outputs and `docker-run.sh` against `agent/{name}/src` existing, so a typo names the available agents instead of silently falling back to one of them.

**Containers.** AgentCore Runtime requires **ARM64** images. Build with `--platform linux/arm64` on an x86 host; emulation setup is in [docs/troubleshooting.md](docs/troubleshooting.md). Build-context exclusions belong in the `.dockerignore` beside each `Dockerfile`, not in the Dockerfile itself.

**Python.** Version 3.12, pinned by `.python-version` in each subproject. Use `uv` for everything. Add dependencies with `uv add <package>==<version>` so they are pinned exactly; never edit `uv.lock` by hand.

## Workflows: adding or changing an agent or MCP server

The shipped `customer-support`, `it-helpdesk`, and `support-tools` entries are illustrative — expect to rename, replace, or add alongside them. These are the procedures for doing that correctly. They capture the sequence and the invariants; the prose walkthrough and every config key live in [GETTING_STARTED.md](GETTING_STARTED.md) and [docs/configuration.md](docs/configuration.md) — link to them, do not restate them.

The binding invariant across all of these: **a directory and its `config.yaml` entry are one change.** Either without the other fails at `cdk synth`. Always finish with the [Verification](#verification) commands.

### Add an agent

1. Create the source directory. Copy `agent/customer-support/` — it is the fully-wired reference (KB retrieval, local tools, MCP client, `utils/`, evals). Copy `agent/it-helpdesk/` instead for a leaner agent with no MCP client or evals.
2. Customize `src/main.py`: the `SYSTEM_PROMPT`, the `tools` list, and the model. Keep tools in `src/tools/` as `@tool` functions returning human-readable strings.
3. Add the `config.yaml` `agents[]` entry. Name it, and optionally set `modelId`, `knowledgeBase` (a name from `knowledgeBases[]`), and `mcpServers` (names from `mcpServers[]`). Omitting `mcpServers` grants access to *all* defined MCP servers; an explicit list scopes it.
4. Do not add a shell script or a `Makefile` target. `chat.sh` and `docker-run.sh` are agent-agnostic and resolve the agent by name from `.rapid/outputs.json`.
5. Do not hardcode the knowledge-base ID or MCP ARNs — CDK injects them as environment variables (enumerated in [docs/configuration.md](docs/configuration.md)).

### Add an MCP server

1. Create the source directory. Copy `mcp/support-tools/` — a FastMCP server with a `Dockerfile` and `.dockerignore`.
2. Define tools in `src/main.py` as `@mcp.tool()` functions; the docstring is the interface the model reads.
3. Add the `config.yaml` `mcpServers[]` entry, then list its name under `mcpServers` on each agent that should reach it.

### Add a knowledge base

1. Create `knowledge-bases/{name}/` and drop documents in it (PDF, TXT, MD, HTML, DOCX); they are uploaded on deploy.
2. Add the `config.yaml` `knowledgeBases[]` entry, then set `knowledgeBase: {name}` on the agents that should retrieve from it.

### Rename or remove

Renaming is a directory rename *and* a `config.yaml` edit together; removal deletes both. A leftover entry pointing at a missing directory, or a directory with no entry, fails at synth. After removing, check no agent still references the deleted `knowledgeBase` or `mcpServers` name.

## Code style

**Python**
- Type hints on every parameter and return
- Docstrings on all public functions; for `@tool` functions the docstring is the interface the model reads, so state what the tool does, its arguments, and what it returns
- Tools return human-readable strings, not raw dicts
- `logger = logging.getLogger(__name__)` per module
- No custom exception classes — raise built-ins with descriptive messages
- No retry logic unless something concrete requires it

**TypeScript (CDK only)**
- `aws-cdk-lib` and `constructs` only; no third-party construct libraries unless they remove substantial complexity
- `RemovalPolicy.DESTROY` is appropriate for prototype resources
- Inline Lambda code is fine under roughly 50 lines
- One stack per deployment; avoid cross-stack references

**Markdown**
- Every fenced code block carries a language tag
- One authoritative file per topic — link, do not duplicate
- No progress annotations or placeholder markers for unimplemented capabilities — work-in-progress labels, unresolved reminder comments, "coming later"; either implement it or leave it out
- Relative links and paths must resolve in a clean clone

## Verification

Run these before reporting a change complete.

```bash
cd infra && npx cdk synth   # required after any change under infra/ or to config.yaml
cd infra && npm test        # Jest: unit, snapshot, and property tests
make doctor                 # prerequisite check (credentials, Docker, Node, Python, jq, Bedrock, bootstrap)
```

`infra/test/` holds three kinds of test. Unit tests cover the config loader and individual constructs. `ac-cdk-deployment.test.ts` asserts against the synthesized template and carries a committed snapshot — a snapshot diff you did not intend is a signal to investigate, not to re-record. `config-properties.test.ts` uses `fast-check` to check loader properties across generated invalid configurations; extend it when you add a validation rule.

For agent behaviour, run the agent locally and talk to it (`make chat`), or use the eval suite under `agent/customer-support/evals/`. Agent tools do not need unit tests.

Contributors run the same commands before submitting; see [CONTRIBUTING.md](CONTRIBUTING.md).

## CI/CD

`make enable-cicd` is opt-in. Once enabled, a push to `main` on the CodeCommit remote triggers only the pipelines whose paths changed:

- `agent/{name}/**` → that agent's pipeline (builds the ARM64 image, updates the AgentCore Runtime)
- `mcp/{name}/**` → that MCP server's pipeline
- `infra/**` or `config.yaml` → the infra pipeline (`cdk synth` + `cdk deploy`)

Those three are the only pipelines the stack instantiates. One agent pipeline and one MCP pipeline is created per `config.yaml` entry; `MonorepoSource` does the path filtering. Frontend changes have no pipeline — redeploy the stack.

## What not to do

- Don't use `pip` — always `uv`
- Don't add retry logic, circuit breakers, or error handling beyond a plain `try`/`except`
- Don't add production-grade monitoring or observability beyond default CloudWatch
- Don't create a new L3 construct for a single-use resource, and don't introduce multi-stack patterns without a stated reason
- Don't restate configuration, troubleshooting, cost, or walkthrough content in this file or in `README.md` — link to the authoritative file
- Don't document a command, a `Makefile` target, or a pipeline that does not exist
- Don't commit `.env` files, credentials, `.rapid/outputs.json`, or anything under `cdk.out/`, `node_modules/`, or `.venv/`
- Don't use `git add .` blindly — stage named paths
- Don't push directly to `main` when CI/CD is enabled; a push deploys
