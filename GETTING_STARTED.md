# Getting Started

The [README](README.md) has the five-command quickstart. This guide is the guided version: it takes you from a clean clone to a deployed agent you have customized for your own use case, and explains enough of the machinery that the next change is yours to make.

By the end you will have the stack deployed in your AWS account, a working conversation with an agent, and one customization of your own — a new tool, a changed prompt, or your own documents in a knowledge base.

---

## Before You Start

You need:

| Requirement | Version | Why |
|---|---|---|
| AWS account and credentials | `aws sts get-caller-identity` succeeds | Everything deploys into your own account |
| [Docker](https://docs.docker.com/get-docker/) | Daemon running | Container images are built locally on first deploy |
| Container architecture | `linux/arm64` | AgentCore Runtime accepts ARM64 images only. Native on Apple Silicon; on an x86/amd64 host this is a cross-architecture build needing buildx and QEMU — setup steps are in [`docs/troubleshooting.md`](docs/troubleshooting.md#cross-platform-build-issues-x86--amd64-hosts) |
| [Node.js](https://nodejs.org/) | 18 or newer | The AWS CDK toolchain under `infra/` |
| [uv](https://docs.astral.sh/uv/) and Python | Python 3.12 | Every Python subproject pins 3.12 via `.python-version`; `uv python install 3.12` installs it |
| Bedrock model access | Enabled in your target region for your `modelId` | The agent cannot invoke a model you have not been granted |

Two steps, then you are ready to deploy:

1. Run the preflight check. It runs eight checks — AWS credentials, Bedrock model access, Docker plus ARM64 build capability, `jq`, `uv`, the Node.js version, the Python version each subproject pins, and CDK bootstrap state — and names both the missing prerequisite and the command that fixes it:

   ```bash
   make doctor
   ```

2. [Bootstrap](https://docs.aws.amazon.com/cdk/v2/guide/bootstrapping.html) CDK, once per account and region. `make doctor` tells you if this is still outstanding and prints this command:

   ```bash
   cd infra && npx cdk bootstrap && cd ..
   ```

## Step 1 — Deploy

Open `config.yaml` at the repository root. It works unmodified — nothing here needs editing to reach a running agent. The two fields you are most likely to touch first are `region` and the `modelId` on your agents.

```yaml
deploymentPrefix: rapid-v1
region: us-west-2
deploymentMode: local
frontendMode: none

knowledgeBases:
  - name: support-docs
  - name: it-docs

agents:
  - name: customer-support
    modelId: global.anthropic.claude-haiku-4-5-20251001-v1:0
    knowledgeBase: support-docs
    mcpServers:
      - support-tools
  - name: it-helpdesk
    modelId: global.anthropic.claude-haiku-4-5-20251001-v1:0
    knowledgeBase: it-docs

mcpServers:
  - name: support-tools
```

`agents` and `mcpServers` are required and have no fallback — omit either and the loader fails with an error naming the key, before any resource is created.

Then deploy:

```bash
make deploy
```

This builds your agent containers locally and stands up the full stack: agent runtimes, memory, knowledge bases, and MCP servers.

**Expect the first deploy to take roughly 15 to 25 minutes** with the shipped configuration. Most of that is the three ARM64 container image builds and the knowledge-base vector index. On an x86/amd64 host the builds run under QEMU emulation and can take twice as long. Later deploys reuse cached image layers and typically finish in 3 to 8 minutes.

When it finishes, the stack writes its outputs to `.rapid/outputs.json`. That file is generated by deployment, machine-local, and not tracked in git — `make chat`, `make logs`, `make ui`, and the evals all read it, so you never copy-paste an ARN.

> Every field: [`docs/configuration.md`](docs/configuration.md). Want a web UI instead of the CLI: [`docs/frontend.md`](docs/frontend.md) — read [`docs/cost-and-teardown.md`](docs/cost-and-teardown.md) first, because every non-`none` frontend mode provisions resources that bill while idle.

## Step 2 — Talk to Your Agent

```bash
make chat
```

This drops you into an interactive conversation with the default agent (`customer-support`). Try something like *"What's your return policy?"* (it answers from the knowledge base) or *"Look up order ORD-1001"* (it calls a sample tool).

To chat with a different agent:

```bash
make chat AGENT=it-helpdesk
```

`AGENT` names an agent from `config.yaml`. If it names one that is not deployed, the command lists the agents that are, rather than quietly connecting you to a different one.

To run an agent as a container on your own machine and talk to that instead of the deployed runtime:

```bash
make docker-run AGENT=customer-support              # builds the ARM64 image, then runs it
make chat AGENT=customer-support CHAT_ARGS=--local  # in a second shell
```

That's the full loop working: runtime, memory, RAG, and tools. Time to customize it.

## What the Sample Agents Cover

Two agents ship, deliberately unequal, so you can see both a fully wired reference and a leaner second instance.

| | `customer-support` | `it-helpdesk` |
|---|---|---|
| AgentCore Runtime and Memory | Yes | Yes |
| Knowledge base (RAG) | `support-docs` | `it-docs` |
| Local Python tools | `lookup_order`, `get_product_info`, `create_support_ticket` | `check_system_status`, `reset_password`, `create_it_ticket`, `get_vpn_config` |
| MCP tools | Explicit `mcpServers: [support-tools]` | No `mcpServers` key, so it inherits every defined MCP server |
| Streaming response helper | Yes — [`agent/customer-support/src/utils/sse.py`](agent/customer-support/src/utils/sse.py) | Yes — [`agent/it-helpdesk/src/utils/sse.py`](agent/it-helpdesk/src/utils/sse.py) |
| Outputs reader for `.rapid/outputs.json` | Yes — [`agent/customer-support/src/utils/outputs.py`](agent/customer-support/src/utils/outputs.py) | **No** — no local helper resolves ARNs for it |
| Evaluation suite | Yes — `agent/customer-support/evals/` | **No `evals/` directory at all.** Copy the one from `customer-support` if you want evals here |

Neither agent demonstrates multimodal document processing, human-in-the-loop approval, or multi-agent handoff. `customer-support` is the one to copy when you add your own.

## Step 3 — Make Your First Change

The agents live in `agent/{name}/src/`. These are the three most common changes. After any of them, run `make deploy` and `make chat` again to see the result.

### Change the system prompt

This defines who your agent is. Edit `SYSTEM_PROMPT` in `agent/customer-support/src/main.py`:

```python
SYSTEM_PROMPT = """You are a helpful assistant for Acme Corp.
Answer questions about our products and help customers track orders."""
```

### Add a tool

Tools are how the agent *does* things. Create a new file in the `agent/customer-support/src/tools/` directory — call it `my_tools.py`:

```python
from strands import tool

@tool
def get_account_balance(account_id: str) -> str:
    """Look up the current balance for a customer account.

    Args:
        account_id: The customer account ID, e.g. ACC-12345
    """
    # Start with mock data, wire to a real API later
    return f"Account {account_id} has a balance of $1,240.00"
```

The docstring matters — the model reads it to decide when and how to call the tool. Then register it in `agent/customer-support/src/main.py`:

```python
from tools.my_tools import get_account_balance

# inside create_agent()
tools = [get_account_balance, ...]
```

Test it locally before deploying: `cd agent/customer-support/src && uv run python main.py`, then `make chat`.

### Add your own knowledge

Drop your documents into a knowledge base directory (PDF, TXT, MD, HTML, DOCX), then trigger a sync:

```bash
# Upload to a specific KB (uses .rapid/outputs.json to resolve the bucket)
make ingest-kb KB=support-docs
```

Or manually:

```bash
aws s3 cp ./my-docs/ s3://$(jq -r '.knowledgeBases["support-docs"].documentsBucketName' .rapid/outputs.json)/kb-source-docs/ --recursive

aws bedrock-agent start-ingestion-job \
  --knowledge-base-id $(jq -r '.knowledgeBases["support-docs"].knowledgeBaseId' .rapid/outputs.json) \
  --data-source-id YOUR_DATASOURCE_ID \
  --no-cli-pager
```

### Iterate quickly without deploying

For fast feedback, run the agent locally instead of deploying each time:

```bash
cd agent/customer-support/src && uv sync && uv run python main.py   # serves on http://localhost:8080
```

In another terminal, point chat at it or run the evals (see [Evaluations](#evaluations)).

## Step 4 — Automate Deployments (Optional)

Everything above works indefinitely with `make deploy` from your machine. CI/CD is a **graduation step**, not part of the happy path: take it when the manual build-and-deploy loop starts costing you more than the setup will.

```bash
make enable-cicd
```

A one-time setup. It seeds your container images to ECR, flips `config.yaml` to `pipeline` mode, deploys the source repository and pipelines, and wires up the git remote. From then on, pushing a change under `agent/{name}/**`, `mcp/{name}/**`, `infra/**`, or to `config.yaml` triggers only the pipeline that owns that path.

**If CodeCommit is not an option for you,** run the same build from GitHub Actions against your own fork. RAPID ships no workflow for this, and adding one means creating three IAM pieces in your account: an IAM OIDC identity provider for `token.actions.githubusercontent.com`, an IAM role whose trust policy is conditioned on the `sub` claim for your repository and branch, and a permissions policy on that role covering ECR push, AgentCore Runtime update, and `sts:AssumeRole` on the CDK bootstrap roles. Until then, deploy locally.

> **Note:** Keep infra and agent/MCP changes in separate commits. Mixed in one commit, both pipelines start at once and can race to update the same stack.

See [CI/CD Graduation](#cicd-graduation-make-enable-cicd) below for exactly what each step does and how to revert.

## Where to Go Next

Four entry points, in order. Each one is a complete stopping place — take the next only when you need what it adds.

**1. Deploy and talk — about half an hour.** Steps 1 and 2 above. You get a deployed agent with memory, RAG, and tools you can hold a conversation with. You defer every customization, the web UI, CI/CD, and any infrastructure decision. If you are still evaluating whether RAPID fits your problem, stop here.

**2. Fit it to your use case — an afternoon.** Step 3, then [Multi-Agent Configuration](#multi-agent-configuration) when one agent is not enough and [MCP Server](#mcp-server) when a tool needs its own container. You get your prompt, your tools, and your documents. You defer automation and any change to the CDK. This is where most prototypes end.

**3. Share it and automate it — about a day.** Step 4 for push-to-deploy, and [`docs/frontend.md`](docs/frontend.md) for a Streamlit UI other people can reach. You get something demonstrable without your laptop in the loop. You defer hardening — read [`docs/cost-and-teardown.md`](docs/cost-and-teardown.md) before you leave a frontend running.

**4. Own the infrastructure — open-ended.** [Infrastructure Customization](#infrastructure-customization) and [Going Beyond Config](#going-beyond-config). You get the L3 constructs used directly and composed however your architecture needs, with `config.yaml` trimmed to whatever is still useful or dropped entirely. You defer nothing — the CDK is now yours to maintain.

Reference material along the way: [How It Works](#how-it-works) for what the stack provisions, [`docs/configuration.md`](docs/configuration.md) for every config key, [Evaluations](#evaluations) for testing agent behaviour systematically, and [`docs/troubleshooting.md`](docs/troubleshooting.md) when something breaks.

## How It Works

RAPID deploys a single CDK stack (`AgentCore-{prefix}`, e.g. `AgentCore-rapid-v1`) that reads `config.yaml` at the repository root and provisions everything your agents need:

```text
config.yaml
    │
    ▼
AgentCore-{prefix}
    ├── AgentCore Agents (one per agents[] entry)
    │     ├── AgentCore Runtime (containerized Strands agent)
    │     └── AgentCore Memory (cross-session persistence)
    ├── Bedrock Knowledge Bases (one per knowledgeBases[] entry)
    │     └── S3 documents bucket
    ├── MCP Server Runtimes (one per mcpServers[] entry)
    └── [Optional] Frontend (Streamlit on Fargate + ALB/CloudFront)
```

The mapping between agents and their resources is config-driven:

- Each agent references a `knowledgeBase` by name → gets `KNOWLEDGE_BASE_ID` injected
- Each agent references `mcpServers` by name → gets MCP runtime ARN(s) injected
- If no `mcpServers` are specified on an agent, it gets access to all defined MCP servers

On deploy, the stack writes its outputs to `.rapid/outputs.json` with a structured format:

```json
{
  "frontendUrl": "...",
  "agents": {
    "customer-support": { "runtimeArn": "...", "runtimeId": "..." },
    "it-helpdesk": { "runtimeArn": "...", "runtimeId": "..." }
  },
  "mcpServers": {
    "support-tools": { "runtimeArn": "...", "runtimeId": "..." }
  },
  "knowledgeBases": {
    "support-docs": { "knowledgeBaseId": "...", "documentsBucketName": "..." },
    "it-docs": { "knowledgeBaseId": "...", "documentsBucketName": "..." }
  }
}
```

Downstream tools — `make chat`, the frontend, and evals — read that file automatically so you never copy-paste ARNs. It is generated state: never edit it expecting a deployment to change, and never commit it.

The default deployment mode is `local`: container images are built from your local source via CDK Docker assets. When you're ready for CI/CD, `make enable-cicd` graduates you to `pipeline` mode with CodeCommit + CodePipeline.

> **This is a starting point.** The config-driven approach handles common patterns out of the box. When you need more flexibility — custom IAM policies, different resource compositions, or integration with existing infrastructure — the underlying CDK constructs are available for direct use. See [Going Beyond Config](#going-beyond-config).

## Multi-Agent Configuration

RAPID supports multiple agents, MCP servers, and knowledge bases — all driven from `config.yaml`. Each gets its own runtime, memory, ECR repo, and CI/CD pipeline.

### Adding a new agent

1. Copy an existing agent directory:

```bash
cp -r agent/customer-support agent/my-new-agent
```

2. In the directory you just created, customize `src/main.py` (system prompt, tools, model).

3. Add to `config.yaml`:

```yaml
agents:
  - name: customer-support
    knowledgeBase: support-docs
    mcpServers:
      - support-tools
  - name: my-new-agent          # ← new
    knowledgeBase: support-docs  # ← optional: reuse or create a new KB
    mcpServers:
      - support-tools           # ← optional: which MCP servers it can call
```

4. Deploy: `make deploy`

### Adding a new MCP server

1. Copy an existing MCP server directory:

```bash
cp -r mcp/support-tools mcp/analytics-tools
```

2. In the directory you just created, edit `src/main.py` to define your tools.

3. Add to `config.yaml`:

```yaml
mcpServers:
  - name: support-tools
  - name: analytics-tools       # ← new
```

4. Reference it from agents that need it:

```yaml
agents:
  - name: customer-support
    mcpServers:
      - support-tools
      - analytics-tools         # ← agent can now call tools from both MCP servers
```

### Adding a new knowledge base

1. Create a documents directory:

```bash
mkdir -p knowledge-bases/my-docs
# Add your documents (PDF, TXT, MD, HTML, DOCX)
cp ~/documents/*.pdf knowledge-bases/my-docs/
```

2. Add to `config.yaml`:

```yaml
knowledgeBases:
  - name: support-docs
  - name: my-docs               # ← new
```

3. Reference it from an agent:

```yaml
agents:
  - name: customer-support
    knowledgeBase: my-docs      # ← now uses the new KB
```

### How agent-to-resource mapping works

```text
config.yaml agents[] entry
    │
    ├── knowledgeBase: "support-docs"  ──→  KNOWLEDGE_BASE_ID env var injected
    │                                        + IAM retrieve permission granted
    │
    └── mcpServers: ["support-tools"]  ──→  MCP_RUNTIME_ARN env var injected (single-agent mode)
                                            MCP_RUNTIME_ARNS env var injected (multi-agent mode, comma-separated)
                                            + IAM invoke permission granted
```

If `mcpServers` is omitted on an agent, it gets access to **all** defined MCP servers. If specified, it gets access only to the listed ones.

## Evaluations

The evals framework tests your agent systematically using [Strands Evals](https://strandsagents.com/). Only `customer-support` ships a suite; `agent/it-helpdesk/` has no `evals/` directory, so copy the one below if you want to evaluate that agent too.

### Define test cases

Edit `agent/customer-support/evals/test_cases.json` or `agent/customer-support/evals/create_experiment.py` to add cases relevant to your agent:

```python
from strands_evals import Case

TEST_CASES = [
    Case[str, str](
        name="account-balance-lookup",
        input="What's my account balance? My account is ACC-12345",
        expected_output="balance",
        metadata={"category": "account", "tool": "get_account_balance"},
    ),
]
```

### Run against the deployed agent

```bash
cd agent/customer-support/evals
uv sync
uv run python eval_agent_acruntime.py
```

The script reads the agent runtime ARN from `.rapid/outputs.json` automatically (or from the `AGENT_RUNTIME_ARN` env var if set).

### Run against a local agent

Start the agent in one terminal:

```bash
cd agent/customer-support/src && uv sync && uv run python main.py
```

Run evals in another:

```bash
cd agent/customer-support/evals && uv run python eval_agent_local.py
```

## MCP Server

MCP (Model Context Protocol) servers let you add tools that run in separate containers from your agents. Useful for tools with different dependencies, tools shared across agents, or tools that need independent scaling.

### Add a tool

Edit `mcp/support-tools/src/main.py`:

```python
@mcp.tool()
def query_inventory(product_id: str, warehouse: str = "all") -> dict:
    """
    Check real-time inventory levels across warehouses.

    Args:
        product_id: Product SKU to check
        warehouse: Specific warehouse or "all" for all locations
    """
    return {
        "product_id": product_id,
        "warehouses": {"east": 150, "west": 89, "central": 234},
    }
```

### Deploy

Push changes and the MCP pipeline deploys automatically (in `pipeline` mode), or run `make deploy` to rebuild locally.

### How agents connect to MCP servers

Agents connect to MCP servers automatically based on the `mcpServers` mapping in `config.yaml`. The CDK stack injects the MCP runtime ARN(s) as environment variables:

- **Single-agent mode** (one agent defined): `MCP_RUNTIME_ARN` (single ARN)
- **Multi-agent mode** (multiple agents defined): `MCP_RUNTIME_ARNS` (comma-separated ARNs)

MCP tools appear alongside built-in tools — no additional agent code needed beyond the MCP client setup in `agent/customer-support/src/tools/mcp_tools.py`.

### Adding a second MCP server

See [Multi-Agent Configuration](#multi-agent-configuration) for adding MCP servers via `config.yaml`.

## Infrastructure Customization

The stack is composed from reusable L3 constructs in `infra/lib/constructs/`. Each construct has its own README with full API documentation. These constructs are the real building blocks — `config.yaml` is just a convenience layer on top.

### Default constructs (wired into the stack)

| Construct | What it does |
|-----------|-------------|
| `AgentCoreAgent` | AgentCore Runtime + Memory for your Strands agent (one per `agents[]` entry) |
| `AgentCoreMCPServer` | MCP server runtime (one per `mcpServers[]` entry) |
| `AgentCorePipeline` | CodePipeline for building + deploying agent/MCP images (one per agent + one per MCP) |
| `CdkDeployPipeline` | Self-mutating CodePipeline for CDK infrastructure changes |
| `BedrockKnowledgeBase` | Bedrock KB with S3Vectors, hierarchical chunking (one per `knowledgeBases[]` entry) |
| `MonorepoSource` | CodeCommit repo with path-based selective pipeline triggering |

### Opt-in constructs (add when needed)

| Construct | What it does |
|-----------|-------------|
| `StreamlitFrontend` | Streamlit on Fargate + ALB. Enabled via `frontendMode`. |
| `CloudFrontFrontend` | CloudFront distribution with VPC Origin. Enabled via `frontendMode: cloudfront`. |
| `CognitoAuth` | Cognito User Pool + hosted UI. Enabled via `frontendMode: public` or `cloudfront`. |
| `MultimodalProcessingPipeline` | BDA-based document processing for PDFs with tables/images. Never instantiated by the default stack — wire it up yourself. |

### Example: add a second data source with advanced parsing

```typescript
// In infra/lib/stacks/agentcore-cdk-stack.ts
const kb = this.knowledgeBases.get('support-docs')!;
kb.addS3DataSource({
  dataSourceName: 'technical-reports',
  bucket: this.kbBuckets.get('support-docs')!,
  inclusionPrefixes: ['reports/'],
  parsingConfig: {
    strategy: ParsingStrategy.BEDROCK_DATA_AUTOMATION,
  },
});
```

### Validating changes

Always run `npx cdk synth` after modifying infrastructure to catch errors before deploying:

```bash
cd infra && npx cdk synth
```

## Going Beyond Config

The `config.yaml` approach is great for getting started quickly and for common patterns. But this project is a starting point — not a boundary. As your needs grow, you have full flexibility to use the CDK constructs directly.

### When to move beyond config

- You need custom IAM policies, VPC placement, or resource configuration not exposed by config
- You want to compose constructs differently (e.g., one agent with multiple knowledge bases)
- You're building a standalone CDK project and want to pull in just the constructs you need
- You want to integrate with existing infrastructure (existing VPCs, existing pipelines, etc.)

### Using constructs directly

Every construct in `infra/lib/constructs/` works independently — they don't require the config-driven stack. You can create your own stack that imports and composes them however you want:

```typescript
import { AgentCoreAgent } from '../constructs/agentcore-agent';
import { BedrockKnowledgeBase } from '../constructs/bedrock-knowledge-base';
import { AgentCoreMCPServer } from '../constructs/agentcore-mcp-server';

// Create resources directly — no config.yaml needed
const kb = new BedrockKnowledgeBase(this, 'MyKB', {
  knowledgeBaseName: 'my-custom-kb',
  description: 'Custom knowledge base',
});

const mcpServer = new AgentCoreMCPServer(this, 'MyMCP', {
  runtimeName: 'my_mcp_server',
  mcpAssetPath: '../mcp/my-tools/src',
});

const agent = new AgentCoreAgent(this, 'MyAgent', {
  runtimeName: 'my_agent',
  agentAssetPath: '../agent/my-agent/src',
  modelId: 'global.anthropic.claude-haiku-4-5-20251001-v1:0',
  environmentVariables: {
    KNOWLEDGE_BASE_ID: kb.knowledgeBaseId,
    MCP_RUNTIME_ARN: mcpServer.runtime.agentRuntimeArn,
  },
});

// Wire permissions
kb.grantRetrieve(agent.runtime);
mcpServer.runtime.grantInvoke(agent.grantPrincipal);
```

### Recommended approach

Start with `config.yaml` to get deploying fast. When you hit a wall or need more control, drop down to the constructs directly. You can:

1. **Extend the existing stack** — add custom resources alongside the config-driven ones in `agentcore-cdk-stack.ts`
2. **Create a parallel stack** — write your own stack in `infra/lib/stacks/` using the constructs
3. **Fork and simplify** — strip out the config layer entirely and hardcode what you need

Each construct has its own README in `infra/lib/constructs/{name}/` documenting its full API.

## CI/CD Graduation (`make enable-cicd`)

CI/CD is **opt-in** — the default quickstart deploys entirely from local Docker builds. When you're ready for automated deployments on push, graduate to pipeline mode. This path depends on AWS CodeCommit; see the caveat in [Step 4](#step-4--automate-deployments-optional).

### What it does

`make enable-cicd` performs these steps in order:

1. **Seed ECR** — builds ARM64 container images for each agent and MCP server locally and pushes them to ECR as `:latest`
2. **Flip config** — sets `deploymentMode: pipeline` in `config.yaml`
3. **Deploy** — runs `npx cdk deploy --all`, which creates the CodeCommit repository and per-agent/per-MCP CodePipelines
4. **Configure git remote** — adds the CodeCommit repo URL as a git remote
5. **First push** — pushes `main` to CodeCommit, activating the pipelines

### After enabling CI/CD

- Changes to `agent/{name}/**` → that agent's pipeline (ARM64 build → ECR → Runtime update)
- Changes to `mcp/{name}/**` → that MCP server's pipeline
- Changes to `infra/**` or `config.yaml` → the infra pipeline (`cdk synth` + `cdk deploy`)

Each agent and MCP server has its own independent pipeline, so a change to `agent/customer-support/` only rebuilds that agent — not `it-helpdesk` or the MCP server.

> **Tip:** Keep infra and agent/MCP changes in separate commits. Mixing them in one commit starts both pipelines simultaneously, which can cause a race condition when both try to update the same CloudFormation stack.

### Failure handling

If any step fails, the command restores `deploymentMode: local` in `config.yaml` and reports which step failed. Your deployment state remains unchanged.

### Reverting to local mode

To go back to local deploys, set `deploymentMode: local` in `config.yaml` and run `make deploy`. The CodeCommit repo and ECR images are retained but the pipelines are removed from the stack.
