# Troubleshooting

confirms each one, and the log source that tells you what actually happened.

## Version and Architecture Requirements

`make doctor` verifies all of these before you deploy. If a check fails it names
both the missing prerequisite and the command that fixes it.

| Requirement | Value | Notes |
|---|---|---|
| Node.js | **18 or newer** | Needed for the AWS CDK toolchain under `infra/`. `make doctor` fails below major version 18. |
| Python | **3.12** | Pinned by the `.python-version` file in each Python subproject. `uv` manages the interpreter; `uv python install 3.12` installs it. |
| Container architecture | **`linux/arm64`** | Amazon Bedrock AgentCore Runtime accepts ARM64 images only. Native on Apple Silicon; on x86/amd64 hosts it is a cross-architecture build — see [Cross-platform build issues](#cross-platform-build-issues-x86--amd64-hosts). |

Also required: the AWS CLI with working credentials, a running Docker daemon,
[`uv`](https://docs.astral.sh/uv/), [`jq`](https://jqlang.github.io/jq/), and a
CDK-bootstrapped target region.

`jq` is not optional. `make deploy` writes `.rapid/outputs.json` with it after
the stack is created, and `make chat`, `make ui`, `make logs`, and `make
ingest-kb` all read that file with it. `make doctor` checks for it so that a
missing `jq` surfaces before a deploy rather than halfway through one.

## Problem Table

| Problem | Check | Log source |
|---|---|---|
| Agent not responding | `make logs` → check for errors; verify model access in the Bedrock console for your configured `region` | `make logs`, or CloudWatch log group `/aws/bedrock-agentcore/runtimes/<runtime-name>-DEFAULT` |
| KB returns no results | Documents uploaded to the `kb-source-docs/` prefix? Sync job completed? | Bedrock console → Knowledge base → Data source → **Sync history** |
| CI/CD pipeline failing | CodeBuild logs in the AWS Console; verify the ARM64 Dockerfile builds locally | CodeBuild project logs in CloudWatch, reachable from the pipeline's failed action |
| Tools not being called | Check docstring clarity; verify the tool is in the `tools` list in `create_agent()` | `make logs` — Strands logs each tool-selection decision; set `DEBUG=true` for verbose tracing |
| CDK deploy error | Run `cd infra && npx cdk synth` first; check CDK bootstrap ran | CloudFormation console → stack `AgentCore-{prefix}` → **Events** tab |
| MCP tools not available | Verify the MCP server deployed; check `make logs` for connection errors | `make logs` for the agent, plus the MCP runtime's own `/aws/bedrock-agentcore/runtimes/<runtime-name>-DEFAULT` log group |
| `make chat` says "run a deploy first" | `.rapid/outputs.json` exists? | None — this is local state, not a service failure. Run `make deploy` to generate it. |
| `NoCredentialsError` from a local container | See [Local container credentials](#local-container-credentials) below | The `make docker-run` terminal — the container logs the botocore traceback |
| `exec format error` during deploy/build (x86 host) | ARM64 cross-build issue — see [Cross-platform build issues](#cross-platform-build-issues-x86--amd64-hosts) below | Local `docker buildx inspect --bootstrap` output; the failing `docker build` step in the `make deploy` output |

`.rapid/outputs.json` is generated by deployment, is machine-local, and is not
tracked in git. Several of the local commands (`make chat`, `make logs`,
`make ui`) read it, so they all fail the same way before a first successful
deploy.

## Local container credentials

A container started by `make docker-run` needs AWS credentials to call Bedrock.
`scripts/docker-run.sh` resolves them on the host and passes the resulting keys
in as environment variables, in this order:

1. `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`, if already
   set in your shell.
2. `aws configure export-credentials`, which runs your host credential chain.
   This covers static profiles, `credential_process`, SSO, and assume-role.
   Pick a profile with `AWS_PROFILE`:

   ```bash
   AWS_PROFILE=my-profile make docker-run AGENT=customer-support
   ```

The container's `~/.aws` is deliberately not a mount of yours. Mounting it fails
for most real setups — `credential_process` and `sso_session` need host binaries
or a host token cache the image does not have, and the files are usually mode 600
owned by your host uid while the image runs as uid 1000.

If credentials cannot be resolved, `docker-run.sh` says so at startup and lists
the profiles in `~/.aws`. The container still starts, so a request made anyway
fails on the first turn with `NoCredentialsError`. Two things to check:

- **The profile resolves at all.** `aws sts get-caller-identity --profile <name>`
  should succeed on the host. Temporary credentials also expire — `docker-run.sh`
  prints the expiry, and the container has to be restarted after it passes.
- **The profile is for the right account.** The container calls Bedrock in the
  region the agent was deployed to, taken from its runtime ARN in
  `.rapid/outputs.json`. A working profile for a different account gets you
  `AccessDeniedException` rather than a missing-credentials error.

## Cross-platform build issues (x86 / amd64 hosts)

AgentCore Runtime only accepts **ARM64** container images. `make deploy` (and the
`make enable-cicd` seed step) builds those images locally, so on an **x86/amd64**
host the build is cross-architecture and needs Docker BuildKit (`buildx`) plus QEMU
emulation. On **Apple Silicon / ARM** hosts the build is native and this section
doesn't apply.

`make doctor` flags this before you deploy. Typical symptoms when it isn't set up:

```text
The requested image's platform (linux/arm64) does not match the detected host platform (linux/amd64)
exec /bin/sh: exec format error
The legacy builder is deprecated ... Install the buildx component to build images with BuildKit
```

**Fix (one-time per machine):**

1. Install the Docker buildx plugin if `docker buildx version` fails:

   ```bash
   # Ubuntu/Debian (distro repo)
   sudo apt install -y docker-buildx
   #   (Docker's official apt repo names it 'docker-buildx-plugin' instead)
   # Amazon Linux / RHEL / Fedora
   sudo dnf install -y docker-buildx-plugin        # or: sudo yum install -y docker-buildx-plugin
   # Manual binary (any distro): https://github.com/docker/buildx#manual-download
   ```

2. Make `docker build` use buildx/BuildKit (CDK shells out to `docker build`):

   ```bash
   docker buildx install
   ```

3. Register QEMU emulators for arm64 (re-run after a reboot if needed):

   ```bash
   docker run --privileged --rm tonistiigi/binfmt:qemu-v9.2.2-53 --install arm64
   ```

   `tonistiigi/binfmt` is the image referenced by Docker's
   [multi-platform build docs](https://docs.docker.com/build/building/multi-platform/);
   it's maintained by a Docker/BuildKit maintainer. **Docker Desktop already bundles
   QEMU**, so this step is only needed on bare Docker Engine (e.g. a Linux CI/dev box).

4. Verify and re-deploy:

   ```bash
   docker buildx inspect --bootstrap | grep -i platforms   # should list linux/arm64
   make deploy
   ```

Note: emulated arm64 builds on amd64 are noticeably slower (especially dependency
install layers) but produce a correct image. For long-lived x86 dev boxes, an
alternative is to skip local builds and let CodeBuild (native ARM64) build the
images via `make enable-cicd`.

In CI/CD the same requirement applies to the pipelines themselves. Every CodeBuild
project the stack creates — the per-agent and per-MCP build projects, and the infra
pipeline's `cdk deploy` project — runs on ARM64 compute (`ARM_CONTAINER`) in
privileged mode, because the infra deploy still builds the frontend image asset. An
`exec /bin/sh: exec format error` in the infra pipeline's `npx cdk deploy` output
means that project is on an x86 image; check its environment type in the CodeBuild
console.

## Reading Logs Directly

`make logs` tails the first agent's runtime log group. To reach a specific
runtime, or an MCP server's logs, derive the group name from the ARN recorded in
`.rapid/outputs.json`:

```bash
# Runtime ARN format: arn:aws:bedrock-agentcore:<region>:<account>:runtime/<runtime-name>
aws logs tail "/aws/bedrock-agentcore/runtimes/<runtime-name>-DEFAULT" \
  --follow --region <region>
```

For build and deploy failures the log source is CloudFormation, not CloudWatch:
the stack **Events** tab names the failing logical resource and the reason,
which is almost always more specific than the error the CLI prints.

## Configuration Errors

The stack validates `config.yaml` before provisioning anything, so an invalid
configuration costs you no resources. Errors name the offending key, the value
received, and the accepted values:

```text
Invalid config: "<key>" has value "<received>" but must be <constraint>.
```

If the message names a key you did not expect to matter, check it against the
reference table in [`docs/configuration.md`](configuration.md). Two keys are
required and have no fallback: `agents` and `mcpServers`.
